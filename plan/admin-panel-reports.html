Admin Panel Reports & Analytics

SuperAdmin reporting suite for the WhatsApp CRM — packages purchased by date range, company balances, a platform KPI dashboard, and usage analytics.

Status Draft for approval

The Ask

Requested by the client (Dushan) for the admin panel:

  • Packages purchased per date range — how many plans/packages were bought in a given period.
  • Option to check balances — remaining message quota per company.
  • Dashboard — at-a-glance platform health and KPIs.
  • Other admin analytics — usage trends across tenants.
Feasibility: Yes, and low-risk. The codebase already has the SuperAdmin role, 4-layer access control, and a cross-tenant Monitoring feature to copy. Every report is built from existing tables (Subscription, Plan, Message, Company) — no new database tables are needed.

Decisions (confirmed)

TopicDecision
"Packages purchased" sourceBoth — show new sign-up counts and revenue side by side.
Revenue figure (for now)Derived from Plan.Price × subscriptions created in range. Stripe/Invoice revenue layered in later.
Stripe billingNot live — ignore Invoice table for v1; design so it can be added later.
AccessSuperAdmin only, under /superadmin/reports.
DeliverableRead-only reports. No edits/writes to billing data.

Implementation Steps

Step 1 · Backend
Create the AdminReports feature
📄 wa_api/wa_api/Features/AdminReports/

Scaffold a new feature folder following the Subscriptions pattern: Controllers/AdminReportsController.cs, IAdminReportsService.cs, AdminReportsService.cs, and a Dtos/ folder. Controller is decorated [Authorize(Roles = "SuperAdmin")]; all read queries use IgnoreQueryFilters() to span every tenant.

[ApiController]
[Route("admin-reports")]
[Authorize(Roles = "SuperAdmin")]
public class AdminReportsController : ControllerBase
{
    private readonly IAdminReportsService _svc;
    // GET endpoints only -> delegate to service, return ResponseHelper.Ok(...)
}

Register in Program.cs: builder.Services.AddScoped<IAdminReportsService, AdminReportsService>();

Step 2 · Backend
Packages-purchased endpoint
📄 GET /api/v1/admin-reports/packages?from=&to=

Count subscriptions created in the range, grouped by plan, with a derived revenue total. Returns both count and revenue per the "Both" decision.

// PackagesReportResponse
{
  from, to,
  totalPackages,            // count of subscriptions created in range
  totalRevenue,             // SUM(plan.Price) for those subscriptions
  byPlan: [ { planName, price, count, revenue } ],
  byDay:  [ { date, count, revenue } ]   // for the chart
}
Revenue is computed from Plan.Price for now because Stripe is not live. When invoices go live, swap the revenue source to Invoice.AmountPaid without changing the response shape.
Step 3 · Backend
Balances endpoint
📄 GET /api/v1/admin-reports/balances

Return every company's remaining message quota and a low-balance flag. Reuses the existing subscription aggregation logic.

// BalanceRow[]
{
  companyId, companyName, planName,
  monthlyQuota,             // Plan.MonthlyMessageQuota
  used,                     // Subscription.MessagesUsedThisPeriod
  remaining,                // quota - used
  periodEnd,                // CurrentPeriodEnd
  isLow                     // remaining < 10% of quota
}
Step 4 · Backend
Dashboard KPI endpoint
📄 GET /api/v1/admin-reports/dashboard

Single call returning the headline platform numbers for the dashboard summary cards.

// DashboardResponse
{
  totalCompanies, activeCompanies,
  activeSubscriptions,
  packagesSoldThisMonth, revenueThisMonth,
  newSignupsThisMonth,
  messagesSent30d, billableMessages30d,
  companiesLowBalance       // count of isLow == true
}
Step 5 · Backend
Usage analytics endpoint
📄 GET /api/v1/admin-reports/usage?from=&to=

Per-company and per-day message volume (sent / delivered / failed / billable) over the range — the "other admin analytics" bucket. Grouped from the Message table.

Step 6 · Frontend
Create the admin-reports feature folder
📄 wa_web/features/admin-reports/

Follow the Users / Monitoring feature pattern: services/ (axios calls), hooks/ (TanStack Query), components/, and types.ts. No Zod form schema needed since reports are read-only (only a date-range filter).

Step 7 · Frontend
Reports page with tabbed reports
📄 wa_web/app/(protected)/superadmin/reports/page.tsx

Server component with the standard SuperAdmin session guard (redirect("/unauthorized") for non-SuperAdmin). Renders a client dashboard with tabs:

  • Dashboard — KPI summary cards (reuse the card style from CompanyHealthTable).
  • Packages — date-range picker → table + bar chart, with CSV export.
  • Balances — company table, remaining-quota column, low-balance rows highlighted.
  • Usage — per-company message volume over the selected range.

Add the Reports link to the SuperAdmin navigation.
