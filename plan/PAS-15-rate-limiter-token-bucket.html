Send-Throttle Hardening — Token-Bucket Rate Limiter (Phase 6.1)

1 · Why this matters — the two halves of "don't get blocked"

A WhatsApp number gets restricted by Meta through two independent mechanisms, and the platform needs a guard on each. They are easy to conflate:

MechanismWhat trips itGuard
Throughput / pacing API calls arriving faster than the number's messages-per-second ceiling, or exceeding the rolling 24-hour business-initiated tier cap (1K / 10K / 100K unique recipients). This plan (6.1). Token bucket + daily tier counter.
Quality / reputation Recipients tapping Block / Report. Quality rating drops Green → Yellow → Red; Red disables messaging. Already built (10.2 monitoring) — surfaces per-company block/failure rates so an abuser is paused before Meta reacts.
Treat 6.1 and 10.2 as a pair. This plan covers the pacing half. The reputation half is the monitoring dashboard already shipped. Neither alone is sufficient; together they are the "number never gets blocked" story.

2 · What is actually wrong today (honest audit)

Current limiter: FixedWindowWabaRateLimiter — an atomic Redis INCR on key rl:waba:{phoneNumberId}:{epochMinute}, default 80 per minute, throwing RateLimitException over the limit. Three distinct problems, in priority order:

① Permanent campaign stall the real bug

CampaignBatchSendJob has no [AutomaticRetry] attribute, so it inherits Hangfire's default of 10 attempts. The batch-chaining call (jobClient.Enqueue<CampaignBatchSendJob>) is only reached on a successful run — never on the throw path. So when rate-limit throws exhaust the 10 retries, the campaign is wedged: Status = Running, recipients stuck Queued, HangfireJobId pointing at a dead job, and nothing alive to resume it. This is concrete, reproducible, and the strongest reason to act.

② Wasted work & thundering herd

Every throw discards the in-flight batch loop and schedules a retry. Multiple concurrent campaigns hit the shared counter, all throw, all back off on Hangfire's synchronized schedule, all wake and rush the limiter together — re-colliding in lockstep. Throughput collapses to a fraction of capacity.

③ Boundary burst + no tier awareness safety

The fixed window resets instantly at each minute rollover: up to 80 sends at :59 and 80 more at :00 = ~160 calls in ~1–2 s. At the current 80/min config the sustained rate is a tame ~1.3/s, but that rollover spike can momentarily approach Meta's per-second ceiling. Separately, the limiter is blind to the number's 24-hour tier (a fresh number is capped at ~1K unique recipients/day; the limiter would happily wave through far more).

Correction worth stating plainly: the abort path does not double-send. Each successful send commits its Message + Sent status immediately, and the catch block calls SaveChangesAsync before re-throwing, so a retried batch re-queries only Status == Queued rows. No recipient is messaged twice. The problems above are real; duplicate delivery is not one of them.

3 · Design decisions

DecisionChoiceWhy
AlgorithmRedis token bucket via a single Lua script Atomic (Redis is single-threaded per script), time-based (no window edge), works across all replicas. Smooth sustained rate and bounded burst.
Clock sourceredis.call('TIME') inside the script One clock for all replicas — immune to per-host clock skew.
Consumption contractNon-throwing TryAcquireAsync returning { Allowed, RetryAfter, Reason } Each caller picks its own waiting policy; no exception-as-control-flow.
Interactive pathWait a short bounded time, else 429 A human is on the HTTP request; single sends almost always get an instant token.
Campaign pathSub-second wait → send same recipient; otherwise reschedule the batch (Hangfire Schedule + jitter), never throw Guarantees forward progress, kills the stall + herd, frees the worker. Safe because the send has not happened when we wait/reschedule.
Daily tier capRedis Set of contact-ids per number per UTC day (SADD/SCARD) Exact unique-recipient count = Meta's actual model. Memory bounded by tier, auto-expires in 25 h.
Tier storageNew MessagingTier column on WabaConnection (+ migration) Limiter must know the cap. SuperAdmin-settable; later auto-synced (Phase 3).
Redis outageFail-safe, not fail-open: per-process in-memory bucket at a low fallback rate; log loudly Today's IncrementAsync returns 0 (allow) on cache error — that removes the guard exactly when a burst is most dangerous. Never fully open.
ValuesAll rates/caps are config with conservative defaults Design must not depend on a hardcoded Meta number; tune without redeploying logic.
The headline win: a token bucket lets us be both faster and safer than today — raise sustained throughput (campaigns finish quicker) while eliminating the rollover burst.

4 · Phase 1 — Token bucket + graceful consumption ships first, materially safer

Phase 1 alone fixes the stall, the herd, and the burst. No DB migration; tier cap arrives in Phase 2.

Step 1.1 · The contract
Non-throwing limiter interface
Infrastructure/RateLimiting/IWabaRateLimiter.cs EDIT 
// recipientContactId: pass the contact for business-initiated sends (campaigns) so they count
// toward the 24h unique-recipient tier cap. Pass null for session/service replies (inbox within
// the 24h window) — those do NOT consume the tier, only the per-second bucket.
public interface IWabaRateLimiter
{
    Task<RateLimitResult> TryAcquireAsync(
        string phoneNumberId,
        Guid? recipientContactId,
        int dailyTierLimit,
        CancellationToken ct = default);
}

public enum RateLimitReason { Ok, PerSecondThrottle, DailyTierExceeded }

public readonly record struct RateLimitResult(bool Allowed, TimeSpan RetryAfter, RateLimitReason Reason)
{
    public static readonly RateLimitResult Allow = new(true, TimeSpan.Zero, RateLimitReason.Ok);
}

In Phase 1, dailyTierLimit is accepted but the daily check is a no-op (returns PerSecondThrottle only). Phase 2 activates it. This keeps call sites stable across phases.

Step 1.2 · The algorithm
Token-bucket Lua script (atomic, cross-replica)
Infrastructure/RateLimiting/RedisTokenBucketRateLimiter.cs NEW infra 
-- KEYS[1] = bucket hash key  rl:tb:{phoneNumberId}
-- ARGV[1] capacity  ARGV[2] refill/sec  ARGV[3] want  ARGV[4] ttlSeconds
-- returns { allowed(1/0), retryAfterMs }
local cap    = tonumber(ARGV[1])
local refill = tonumber(ARGV[2])
local want   = tonumber(ARGV[3])
local ttl    = tonumber(ARGV[4])

local t   = redis.call('TIME')                      -- single clock for all replicas
local now = tonumber(t[1]) + tonumber(t[2]) / 1000000.0

local d      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(d[1])
local ts     = tonumber(d[2])
if tokens == nil then tokens = cap; ts = now end

tokens = math.min(cap, tokens + math.max(0, now - ts) * refill)  -- refill by elapsed

local allowed, retry = 0, 0
if tokens >= want then
  tokens  = tokens - want
  allowed = 1
else
  retry = math.ceil(((want - tokens) / refill) * 1000)
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], ttl * 1000)          -- sliding TTL: idle keys self-clean
return { allowed, retry }

Loaded once and invoked with IDatabase.ScriptEvaluateAsync (mirrors the existing RedisDistributedLockService Lua pattern). capacity = burst ceiling, refill = sustained mps — both from config (Step 1.5).

Step 1.3 · Fail-safe fallback
In-process bucket when Redis is absent or erroring
Infrastructure/RateLimiting/InProcessTokenBucket.cs NEW
  • Same token-bucket math, guarded by a SemaphoreSlim per phone-number id (mirrors the existing in-memory IncrementAsync fallback).
  • Used when REDIS_CONNECTION is unset (dev) and as the catch-path when a live Redis call throws — the limiter degrades to local pacing instead of failing open.
  • Fallback refill is a low config value: across R replicas the worst case is R× that rate, so it must stay comfortably under Meta's ceiling. Every fallback hit logs at Warning.
The one behaviour we never restore: fail-open. A rate limiter that allows everything when its backing store is down is worse than no limiter, because it bursts precisely during infra trouble.
Step 1.4 · Caller policies
Two waiting strategies over the same primitive
Infrastructure/RateLimiting/WabaRateLimiterExtensions.cs NEW Features/Messages/WhatsAppMessageSender.cs EDIT Features/Campaigns/Jobs/CampaignBatchSendJob.cs EDIT

Interactive (sender) — short wait, else 429

// WhatsAppMessageSender.SendAsync — session reply, so recipientContactId = null (skips tier cap)
await rateLimiter.AcquireOrThrowAsync(
    waba.PhoneNumberId, recipientContactId: null, dailyTierLimit: 0,
    maxWait: TimeSpan.FromSeconds(2), ct);                // extension: loops Task.Delay up to maxWait
// on timeout → throw RateLimitException → existing 429 envelope. Single sends almost never wait.

Campaign (background) — sub-second wait, else reschedule

const int WaitCapMs = 750;   // only ever block a Hangfire worker for sub-second pauses

var r = await rateLimiter.TryAcquireAsync(
    waba.PhoneNumberId, recipient.ContactId, tierLimit, ct);

if (!r.Allowed && r.Reason == RateLimitReason.PerSecondThrottle
              && r.RetryAfter.TotalMilliseconds <= WaitCapMs)
{
    await Task.Delay(r.RetryAfter, ct);                   // send hasn't happened yet → safe
    r = await rateLimiter.TryAcquireAsync(waba.PhoneNumberId, recipient.ContactId, tierLimit, ct);
}

if (!r.Allowed)
{
    await db.SaveChangesAsync(ct);                        // persist progress; recipient stays Queued
    var delay = r.Reason == RateLimitReason.DailyTierExceeded
        ? DelayUntilNextUtcDay()                          // tier resets at the 24h boundary
        : TimeSpan.FromSeconds(5 + Random.Shared.Next(0, 10));  // jitter breaks the herd
    campaign.HangfireJobId = jobClient.Schedule<CampaignBatchSendJob>(
        j => j.RunAsync(campaignId, CancellationToken.None), delay);
    await db.SaveChangesAsync(ct);
    return;                                               // clean exit — NO throw, NO stall
}
// ... proceed to send this recipient exactly as today ...
  • Worker starvation guard: WorkerCount = max(4, cores×2) is shared with the default queue, so a campaign may only block a worker for sub-second waits. Anything longer is a Schedule, which releases the worker immediately.
  • Jitter is mandatory. Without the random offset, every throttled campaign reschedules to the same instant and rebuilds the herd at wake-up.
  • On daily-tier exceed: emit a Notification ("Campaign throttled — daily limit reached, resuming after reset") via the existing Notifications feature.
Step 1.5 · Fixing the stall directly
Bound retries so a crash can never wedge a campaign
Features/Campaigns/Jobs/CampaignBatchSendJob.cs EDIT
  • Add an explicit [AutomaticRetry(Attempts = N, OnAttemptsExceeded = AttemptsExceededAction.Delete)] so a genuinely failing batch (not rate-limit — that path no longer throws) dead-letters predictably instead of silently exhausting the default 10.
  • Add a lightweight campaign-sweeper recurring job (or extend an existing recurring job): find campaigns Running with Queued recipients but no live Hangfire job, and re-enqueue. A belt-and-braces backstop so no campaign can ever be permanently stranded.

5 · Phase 2 — Daily tier cap + MessagingTier column tier-aware

Step 2.1 · Schema
Store each number's tier

                            Tier100K = 100000, Unlimited = int.MaxValue }

// new column; default Tier1K — the conservative assumption for a freshly connected number
public MessagingTier MessagingTier { get; set; } = MessagingTier.Tier1K;

SuperAdmin can edit it on the WABA-connections screen (small form addition, optional in this phase). The campaign job reads (int)waba.MessagingTier for dailyTierLimit.

Step 2.2 · The counter
Exact unique-recipient daily cap (Lua + Redis Set)
Infrastructure/RateLimiting/RedisTokenBucketRateLimiter.cs EDIT 
-- KEYS[1] = rl:day:{phoneNumberId}:{yyyyMMdd-UTC}    ARGV[1]=contactId  ARGV[2]=limit  ARGV[3]=ttl
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then return 1 end  -- already counted today
if redis.call('SCARD', KEYS[1]) >= tonumber(ARGV[2]) then return 0 end -- would exceed tier
redis.call('SADD', KEYS[1], ARGV[1])
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[3]))                     -- ~25h, rolls off next day
return 1

Order of operations in TryAcquireAsync: token bucket first (per-second), then the daily Set check only when recipientContactId != null. A 0 from the daily script returns { Allowed=false, Reason=DailyTierExceeded }, which the campaign job maps to the "reschedule to next UTC day" branch already written in Step 1.4.

Counting model — chosen, with the tradeoff stated: a Redis Set gives an exact unique-recipient count, matching Meta's tier definition. Cost: up to tierLimit contact-ids per number per day (~3–4 MB at the 100K tier), auto-expiring in 25 h — acceptable. The rejected alternative, a plain message INCR, is simpler but under-delivers: it counts repeat messages to the same person against the cap, silently choking legitimate campaigns. Given the safety priority, exact-unique is the right call.

6 · Phase 3 — Auto-sync tier & quality from the health check optional, low-cost

Step 3.1 · Use data we already fetch
Persist Meta's reported tier & quality
Infrastructure/Jobs/WabaHealthCheckJob.cs EDIT
  • WabaHealthCheckJob already requests quality_rating in its fields list and then discards it. Add messaging_limit_tier to the same request and persist both.
  • Map Meta's messaging_limit_tier (TIER_1K / TIER_10K / TIER_100K / TIER_UNLIMITED) → the MessagingTier enum, and store quality_rating (GREEN/YELLOW/RED) on the connection.
  • The limiter then becomes self-tuning: as Meta upgrades a number, its daily cap rises automatically — no manual SuperAdmin edit.
  • Bonus: storing quality rating feeds the 10.2 monitoring dashboard (the reputation half), closing the loop between both guards.
Phase 3 is independent and safe to defer. A sane default tier (Tier1K) + SuperAdmin override from Phase 2 is already safe; auto-sync just removes the manual step and adds quality telemetry.

8 · Verification strategy non-negotiable

"Perfect" is meaningless if unverified. The plan ships with tests, not just code.

  1. Concurrency test (the critical one). Fire N = 500 parallel TryAcquireAsync calls for one phone-number id against a real/embedded Redis. Assert: tokens granted in any rolling 1-second slice never exceed PerSecondCapacity + refill, and total grants over T seconds ≈ refill × T (within one bucket). This is the proof the Lua bucket actually bounds the rate under contention — the section most safety plans omit.
  2. Boundary test. Drive sends across a wall-clock minute rollover; assert no spike above the bucket ceiling (the bug the fixed window has).
  3. Daily-cap test. Same contact twice → counts once; (limit+1) distinct contacts → the last returns DailyTierExceeded.
  4. Fail-safe test. Point at a dead Redis; assert calls fall back to the in-process bucket (bounded, logged) and never return unconditional-allow.
  5. Stall regression test. Force sustained throttling mid-campaign; assert the job reschedules (Hangfire Schedule) rather than throwing, recipients remain Queued, and a later run drains them to Sent with zero duplicates.

10 · Definition of Done

  • Phase 1: Total throughput to one number never exceeds its configured per-second bucket regardless of worker/replica count (proven by the concurrency test); rate-limited campaigns reschedule and always finish; Redis outage degrades to a bounded local bucket, never fail-open; the old FixedWindowWabaRateLimiter is deleted.
  • Phase 2: A number never exceeds its MessagingTier unique-recipient cap in a rolling day; over-cap campaigns pause and resume after reset with a tenant notification.
  • Phase 3: Tier & quality auto-sync from Meta via the existing health-check poll; the limiter self-tunes and the monitoring dashboard shows live quality ratings.
  • All five verification tests pass in CI.
Net: Phase 1 is the safety-critical core and is shippable on its own — it removes the burst, the stall, the herd, and the fail-open hole in one change. Phases 2–3 add the tier dimension and make it self-tuning. Combined with the 10.2 monitoring already built, both mechanisms by which Meta blocks a number are now guarded.
