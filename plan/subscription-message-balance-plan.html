Subscription & Message-Balance Plan

How message balance and expiry behave when a company subscribes, re-subscribes, runs out of messages, or lets a plan lapse.

1. Concept

A subscription gives a company two things:

  • A message balance — the number of messages they can send.
  • An expiry date — the date the balance stops being usable.

A company can subscribe again at any time. What happens to their balance and expiry depends on whether their current subscription is still alive at the moment of purchase.

2. Core rule

Sending is allowed only when the plan is NOT expired AND the balance is greater than 0. If either condition fails, sending is blocked until the customer subscribes again.

At purchase time, the system chooses between two paths:

Condition at purchasePathMessagesNew expiry
Current plan is active — not expired and balance > 0 STACK current balance + new plan's messages current expiry + new plan's days
Current plan is expired OR balance = 0 FRESH START new plan's messages only (old leftover discarded) today + new plan's days 
if (not expired AND balance > 0)
    → STACK:  balance += newMessages;   expiry = currentExpiry + newDays
else
    → FRESH:  balance  = newMessages;    expiry = today + newDays

4. Points needing explicit client confirmation

1. Leftover messages are lost when a plan expires. In Scenario 5 the unused 3,000 messages are gone. A customer only gets value from a subscription if they use it or re-subscribe before it expires — the "use it or lose it" rule.
2. Stacking only happens on a live plan. Once expired or emptied to zero, re-subscribing carries nothing over — it is a clean restart from today.
3. One combined pot. Even if a customer "subscribes" several times, they always have a single running balance and a single expiry date — not separate parallel subscriptions.

5. What changes in the system

  • 1
    Re-subscribe becomes "stack or fresh"
    Today, subscribing again cancels the old subscription and replaces it. New behavior: stack onto the live balance/expiry, or start fresh if expired/empty.
  • 2
    Remove the automatic 30-day reset
    The balance now runs continuously until expiry instead of resetting every month.
  • 3
    Send block stays as-is
    The existing gate already enforces "not expired AND balance > 0" — no change required.

Files touched

SubscriptionService.cs Re-subscribe branches into stack (extend balance + expiry) vs. fresh start (reset from today).
SubscriptionPeriodResetJob.cs Disabled / removed — no more monthly usage reset.
SubscriptionGate.cs No change — already blocks on expired OR empty balance.

6. Open question for the client

Do leftover messages carry over after expiry, or are they forfeited? This plan assumes forfeited (Scenario 5). If the client prefers leftover messages to carry over even after a plan lapses, that is a small change — please confirm which behavior is wanted before build.
