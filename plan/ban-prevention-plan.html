Background & Threat Model

This project uses the official Meta Cloud API — not Baileys or whatsapp-web.js. That flips the threat model entirely: Meta won't ban for pacing or automation detection. Restriction comes from policy violations: user reports, ignored opt-outs, and continued sending after Meta signals account health degradation.

Key insight: Rate limiting (already implemented) prevents throttles but cannot prevent bans. The actual ban vectors are all about consent and quality signals, not send speed.

Implementation Order & Rationale

  • 1
    Phase 1 — Opt-out / STOP Detection Highest Risk
    Continuing to message a user after they say STOP is a direct policy violation and the #1 trigger for user reports. Pure backend change — no migration dependency. Must land first.
  • 2
    Phase 2 — Policy Error Code Halting High Risk
    Blind retrying on 131048 (spam rate) or 368 (restricted) worsens account standing. No data model changes needed — this is logic-only in the batch job.
  • 3
    Phase 3 — Quality Rating Reaction Medium Risk
    QualityRating is already being fetched — it just needs to be read in the send path. YELLOW throttles throughput; RED blocks business-initiated sends entirely.
  • 4
    Phase 4 — Opt-in Consent Enforcement Compliance
    Structural change — adds Contact.HasOptedIn, migration, DTO updates, and campaign enforcement. Done last because it requires the widest surface change and has existing data implications.

Step 1.4
Detect STOP keywords in InboundMessageWebhookHandler
📄 Features/Webhooks/Handlers/InboundMessageWebhookHandler.cs

After building the inbound Message, check the body against a stop-intent keyword list. If matched, set contact.IsOptedOut = true and contact.OptedOutAt = now. This runs inside the existing foreach loop — no extra DB round-trip needed. 

private static readonly HashSet<string> StopKeywords = new(StringComparer.OrdinalIgnoreCase)
{
    "stop", "unsubscribe", "cancel", "quit", "end", "opt out", "optout",
    "remove me", "no more", "don't contact", "do not contact"
};

private static bool IsStopIntent(string body)
{
    var trimmed = body.Trim();
    // Exact match or starts-with for short commands like "STOP please"
    return StopKeywords.Contains(trimmed)
        || StopKeywords.Any(k => trimmed.StartsWith(k, StringComparison.OrdinalIgnoreCase));
}

// Inside the foreach (var m in value.Messages!) loop, after building `contact`:
if (IsStopIntent(body) && !contact.IsOptedOut)
{
    contact.IsOptedOut = true;
    contact.OptedOutAt = now;
    logger.LogInformation(
        "Contact {Phone} sent opt-out intent — suppressed from future outbound sends.", phone);
}

Phase 2 — Policy Error Code Halting
Detect Meta's account-level restriction codes and stop campaigns before they worsen account standing
High Risk
Step 2.1
Create MetaPolicyErrorCodes constant class
📄 Features/Messages/MetaPolicyErrorCodes.cs

Centralise the error codes so both the campaign job and any future senders can share the same classification logic.

namespace wa_api.Features.Messages;

public static class MetaPolicyErrorCodes
{
    /// Spam rate limit — message rejected due to spam signals. Pause campaign.
    public const string SpamRateLimit = "131048";

    /// Healthy-ecosystem limit — sending harming broader ecosystem. Pause campaign.
    public const string HealthyEcosystemLimit = "131049";

    /// Account restricted — stop ALL sends for this WABA until resolved.
    public const string AccountRestricted = "368";

    /// Account suspended — stop ALL sends immediately.
    public const string AccountSuspended = "131031";

    /// Returns true if this code represents a per-campaign pause signal.
    public static bool IsCampaignPause(string? code) =>
        code is SpamRateLimit or HealthyEcosystemLimit;

    /// Returns true if this code represents an account-level restriction (all sends must stop).
    public static bool IsAccountRestriction(string? code) =>
        code is AccountRestricted or AccountSuspended;
}
Step 2.2
Halt campaign on policy error codes in CampaignBatchSendJob
📄 Features/Campaigns/Jobs/CampaignBatchSendJob.cs

After calling SendTemplateMessageAsync, inspect the returned errorCode. If it's a campaign-pause code, set campaign.Status = CampaignStatus.Paused and notify the tenant. If it's an account-restriction code, mark the WABA connection as inactive and notify. Do not continue the loop — return immediately to avoid sending more messages. 

if (externalId is null)
{
    // Check for policy violation codes before marking recipient and continuing.
    if (MetaPolicyErrorCodes.IsAccountRestriction(errorCode))
    {
        logger.LogError(
            "Meta returned account restriction code {Code} for WABA {WabaId} — halting all campaigns.",
            errorCode, waba.Id);

        // Deactivate the WABA connection so no further sends can happen.
        waba.IsActive = false;
        campaign.Status = CampaignStatus.Paused;
        await db.SaveChangesAsync(ct);

        await notifier.CreateAsync(
            campaign.CompanyId, campaignId, null,
            Notifications.Entities.NotificationType.CampaignFailed,
            "WhatsApp account restricted",
            $"Meta has restricted your WhatsApp number. All campaigns paused. Error: {errorCode}. " +
            "Please review your account in Meta Business Suite.",
            ct);
        return;
    }

    if (MetaPolicyErrorCodes.IsCampaignPause(errorCode))
    {
        logger.LogWarning(
            "Meta returned spam/ecosystem code {Code} — pausing campaign {CampaignId}.",
            errorCode, campaignId);

        campaign.Status = CampaignStatus.Paused;
        await db.SaveChangesAsync(ct);

        await notifier.CreateAsync(
            campaign.CompanyId, campaignId, null,
            Notifications.Entities.NotificationType.CampaignFailed,
            "Campaign paused — spam signal detected",
            $"Meta flagged this campaign for spam signals (code {errorCode}). " +
            "Campaign paused. Review your template and contact list quality before resuming.",
            ct);
        return;
    }

    // Non-policy failure — mark recipient and continue.
    recipient.Status = RecipientStatus.Failed;
    recipient.ErrorCode = errorCode ?? "SEND_FAILED";
    logger.LogWarning(...);
}

Phase 3 — Quality Rating Reaction
Read the already-stored QualityRating in the send path; throttle on YELLOW, block on RED
Medium Risk
Step 3.1
Gate campaign batch on QualityRating
📄 Features/Campaigns/Jobs/CampaignBatchSendJob.cs

After loading the campaign and WABA connection, check waba.QualityRating before entering the recipient loop. RED blocks the entire batch and notifies the tenant. YELLOW halves the effective batch size to reduce throughput without stopping completely. 

// After loading `waba`, before the recipient loop:
if (waba.QualityRating == "RED")
{
    logger.LogWarning(
        "WABA {WabaId} quality rating is RED — pausing campaign {CampaignId} to protect account.",
        waba.Id, campaignId);

    campaign.Status = CampaignStatus.Paused;
    await db.SaveChangesAsync(ct);

    await notifier.CreateAsync(
        campaign.CompanyId, campaignId, null,
        Notifications.Entities.NotificationType.CampaignThrottled,
        "Campaign paused — low WhatsApp quality rating",
        "Your WhatsApp number has a RED quality rating. Campaign paused to prevent account restriction. " +
        "Improve message quality and opt-in practices, then resume.",
        ct);
    return;
}

// Reduce throughput on YELLOW to let quality recover.
var effectiveBatchSize = waba.QualityRating == "YELLOW" ? BatchSize / 2 : BatchSize;

Then replace the hard-coded Take(BatchSize) in the query with Take(effectiveBatchSize).

Block campaign launch on RED quality rating

Add a pre-launch check in LaunchAsync so tenants can't start new campaigns while the WABA is at RED quality. This is a UX safety net — the batch job already halts if RED is detected mid-run, but blocking at launch gives immediate feedback.

Out of Scope (v1)

  • Frontend UI changes — consent badges, opt-out indicators, and the contact import consent flow are frontend work tracked separately.
  • Account rotation / IP proxying / fingerprinting — irrelevant for the official Cloud API; Meta restricts on policy, not automation detection.
  • Webhooks for quality rating changes — Meta does send phone_number_quality_update webhooks. Wiring those up to auto-react is a future improvement; for now the health-check poll (already implemented) is sufficient.
  • Opt-in collection flows — how tenants collect consent (forms, confirmation messages) is a product feature, not a system safety control.
  • GDPR / data deletion — separate compliance work; opt-out is not the same as data erasure.
