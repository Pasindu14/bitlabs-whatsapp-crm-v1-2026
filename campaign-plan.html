Section 2 — Campaign Status State Machine

Forward-only status transitions — same forward-only rule as Message.Status

Draft → Scheduled → Running → Completed
Running → Paused → Running   |   Running / Scheduled → Cancelled   |   Running → Failed

⚠️ Transition Rules

  • Draft → Scheduled: Only when ScheduleType = OneTime/Recurring and ScheduledAt is set.
  • Draft / Scheduled → Running: On Immediate launch or when the Hangfire job fires.
  • Running → Paused: Manual pause cancels the Hangfire continuation job; stores HangfireJobId = null.
  • Paused → Running: Re-enqueue from last SentCount offset.
  • Running → Completed: When all CampaignRecipient rows are no longer Queued.
  • → Failed: If the job hits max retries or a fatal Meta error.
  • → Cancelled: Explicit user action; remaining Queued recipients flipped to Skipped.

Section 4 — Hangfire Jobs

The background engine that actually sends messages

Fire & Forget / Scheduled

CampaignLaunchJob

🚀
  • Triggered by /campaigns/{id}/launch
  • Snapshot all opted-in contacts from the list into CampaignRecipient rows (status = Queued)
  • Sets TotalRecipients on Campaign
  • Chains into CampaignBatchSendJob (continuation)
  • Wraps in distributed lock — prevents double-launch
Batched Continuation

CampaignBatchSendJob

📦
  • Processes N recipients per batch (e.g. 50 at a time)
  • Each recipient: resolve variable mapping → call WhatsAppMessageSender
  • Rate limiter checked per send — backs off if over cap
  • Uses IdempotencyKey = campaign:{id}:contact:{id}
  • Updates CampaignRecipient.Status + Campaign.SentCount
  • Chains next batch until all Queued rows are exhausted → sets Campaign = Completed
  • Checks Campaign.Status before each batch — exits if Paused/Cancelled
Recurring Cron

CampaignSchedulerJob

🕐
  • Runs every minute via Hangfire recurring
  • Queries all Scheduled campaigns where ScheduledAt <= now
  • Enqueues CampaignLaunchJob for each due campaign
  • For recurring campaigns: after launch, sets next ScheduledAt from cron expression
  • Idempotent — won't double-fire if job already Running
Error Recovery

CampaignPoisonHandlerJob

☠️
  • Triggered when CampaignBatchSendJob exceeds max retries
  • Marks Campaign.Status = Failed
  • Flips remaining Queued recipients → Failed with error code
  • Logs structured error to Serilog with CorrelationId
  • No infinite retry loop — dead-letters the job cleanly

✅ Key Job Rules

  • Every job uses IgnoreQueryFilters + manual CompanyId stamp — no HttpContext in Hangfire scope (per existing project convention).
  • Batch size is configurable via appsettings.json — start at 50, tune by tier.
  • The rate limiter sits inside the batch loop — never bypass it.
  • Subscription gate is checked once at launch time, not per-message (quota deducted per send).

Section 5 — Variable Mapping & Personalization

How template placeholders get filled per contact at send time

Stored as JSONB

VariableMapping Schema

📋

Stored on the Campaign entity. Maps each template variable index to a contact attribute key.

{
  "body": {
    "1": "Name",
    "2": "attributes.company"
  },
  "header": {
    "1": "attributes.offer_code"
  }
}
At Send Time

Variable Resolution

⚡
  • For each contact: load Contact.Name + Contact.Attributes (JSONB)
  • Walk the mapping: replace {{1}} with resolved value
  • If a value is null/missing → skip this recipient (status = Skipped, log reason)
  • Snapshot ResolvedVariables to CampaignRecipient for audit trail
  • Never mutate the original contact — always read-only

Section 8 — Critical Rules & Guardrails

Things that must not be violated during implementation

🔒 Tenancy — No Manual WHERE CompanyId

Campaign and CampaignRecipient must have the global query filter on CompanyId. Hangfire jobs have no HttpContext — use IgnoreQueryFilters() with an explicit CompanyId lookup, same as existing webhook handlers. Never trust a CompanyId passed from the client.

⚡ Rate Limiter is Mandatory

Every single send in CampaignBatchSendJob must pass through FixedWindowWabaRateLimiter before calling WhatsAppMessageSender. Bypassing it risks WABA quality rating damage and account ban. If rate limited, back off and requeue — never drop messages.

✅ Idempotency on Every Send

Use IdempotencyKey = campaign:{campaignId}:contact:{contactId}. This ensures that if CampaignBatchSendJob retries after a failure, the same contact never gets the same campaign message twice. The existing IdempotencyService handles this — just follow the same pattern as WhatsAppMessageSender.

📋 Template Must Be Approved at Launch

The /launch endpoint must validate that the selected template has Status == Approved before enqueuing any jobs. Return a clear ApiError if not. Never launch with a Pending or Rejected template.

❌ Marketing Messages Need Opt-In

For templates with Category == Marketing, only send to contacts where OptInStatus == OptedIn. Contacts without opt-in are silently skipped (status = Skipped, not Failed). This is a compliance requirement — Meta can ban WABAs for marketing messages to opted-out numbers.

Section 9 — Recommended Build Order

Dependency-ordered so each step is testable before the next

1
Backend — Entities + Migration wa_api · Database

Create Campaign and CampaignRecipient entities, add to AppDbContext with global query filters and composite indexes. Generate and apply EF Core migration. Add necessary enums (CampaignStatus, ScheduleType, RecipientStatus).

2
Backend — Repository + Service (CRUD) wa_api · Features/Campaigns

Create ICampaignRepository, CampaignRepository, and CampaignService. Implement create, read (list + by id), update, soft delete, and the stats rollup query. Register in DI.

3
Backend — Controller + DTOs wa_api · Features/Campaigns

Build CampaignsController with all 12 endpoints, request/response DTOs, and [RequirePermission("ScheduleTemplate")] on every endpoint. Test CRUD with a REST client before adding jobs.

4
Backend — Hangfire Jobs wa_api · Infrastructure/Jobs

Implement CampaignLaunchJob, CampaignBatchSendJob, CampaignSchedulerJob (recurring), and CampaignPoisonHandlerJob. Wire /launch and /pause endpoints to enqueue/cancel the right Hangfire jobs. Test with a small contact list.

5
Backend — Status Webhook Integration wa_api · Features/Webhooks

Update the existing MessageStatusWebhookHandler to also update CampaignRecipient.Status when a message's CampaignId is set. The delivery tracking stats should then reflect real Meta callbacks.

6
Frontend — 5-Layer Feature Module wa_web · features/campaigns

Build schema → actions → hooks → store → components in that order. Start with the table + status badge (no wizard yet) to validate the API integration, then layer in the creation wizard, then the detail/stats page.

7
Frontend — Page + Navigation wa_web · app/(protected)/campaigns

Create the page route, add the Campaigns link to app-sidebar nav, apply the ScheduleTemplate permission guard. Add the campaign detail page at /campaigns/[id].
