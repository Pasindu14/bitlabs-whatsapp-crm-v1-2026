Money & billing

6 ISSUES

The category that started this — sends that weren't being charged, and limits that didn't hold.

Messages sent but never counted against the plan

Before Sends through Facebook and campaigns weren't charged to the customer's quota — so they could blow past their paid limit, and it never showed up in usage or reports. This was your original complaint.

Now Every send — direct, campaign, or reply — meters through one shared, atomic path. Nothing goes out uncounted.

A billing retry could hand out a free month

Before Stripe routinely re-delivers payment events. Each delivery re-zeroed the customer's usage mid-month — a fresh full quota, for free, every time it fired.

Now Usage resets only on a genuine renewal, and every billing event is de-duplicated so a retry can't wipe the counter.

Customers could send past what they paid for

Before Near the limit, many sends at once all read "still under" and all went through — quietly overshooting the plan.

Now The cap is enforced at the database in one atomic step — it's physically impossible to reserve past the limit, even under heavy concurrency. Verified against the live database.

Failed messages counted as delivered

Before Reports and usage counted messages that never arrived, so the numbers customers saw were simply wrong.

Now Only real, successful sends count — dashboards and the quota counter finally agree.

Refunds credited the wrong account

Before When a message later failed, the refund could land on a different subscription than the one that was charged — gifting free messages.

Now A refund always returns to the exact plan that paid for the message.

Foreign-currency invoices shown 100× wrong

Before Yen and won invoices (currencies with no decimals) displayed one-hundredth of the real amount.

Now Each currency is formatted by its own rules.

Message delivery

6 ISSUES

What your customers actually experienced on WhatsApp — and what protects your sending number.

The same message delivered twice

Before Overlapping background jobs could send one recipient the same WhatsApp message twice — the exact "I received 2 messages" issue you reported.

Now An atomic claim guarantees one send per recipient, even if two jobs run at once. Zero duplicates confirmed in production.

Recurring campaigns silently stopped forever

Before A recurring campaign sent once, then delivered nothing on every future run — with no error, no warning. A core feature, quietly broken.

Now Each run correctly re-sends to its audience, and its history is kept straight.

A stuck campaign retried forever

Before A campaign that hit one bad message would re-attempt every minute, indefinitely — never marked failed, nobody notified, re-sending earlier recipients each cycle.

Now It gives up cleanly, marks itself failed, and notifies the customer.

A brief network blip permanently killed messages

Before A two-second hiccup reaching WhatsApp marked every message in that window as permanently failed — deliverable customers simply never got them.

Now Temporary errors wait and retry instead of dropping the message.

WhatsApp's ban-protection was silently switched off

Before A one-line data bug disabled every anti-ban safeguard — spam flags, quality warnings, throttling — so a campaign flagged by Meta would keep blasting and risk the number being blocked.

Now The safeguards work again: a flagged campaign pauses itself to protect your number.

An expired token burned the whole audience

Before If a connection's token expired mid-campaign, it failed every remaining recipient one at a time instead of stopping.

Now It halts immediately and flags the connection to reconnect.

Security

4 ISSUES

Protecting your customers' WhatsApp accounts and their logins.

WhatsApp tokens stored in plain text

Before Every customer's WhatsApp access token and app secret sat in the database unencrypted. A single database or backup leak meant full takeover of every tenant's WhatsApp sending.

Now Encrypted at rest with AES-256 — provisioned and verified live in production, with sending confirmed working through the encrypted tokens.

No limit on login attempts

Before Unlimited password guesses per account, per IP — open to password-spraying against a known admin email.

Now Login and token-refresh are rate-limited.

Logins stayed valid for 8 hours

Before Deactivating a user or changing their role didn't take effect for up to eight hours.

Now Sessions are 60 minutes, refreshed silently in the background.

One stray webhook could mute everyone

Before An event for a number not yet in the system returned an error — and enough of those could make Meta disable incoming notifications for all customers on the shared endpoint.

Now Unroutable events are safely acknowledged and dropped, protecting everyone's inbound.

Reliability & scale

4 ISSUES

The things that break the moment you grow past one server or run under real load.

Live chat broke on a second server

Before The instant you ran more than one server, realtime inbox updates silently stopped reaching half your users — no error, just a dead inbox until refresh.

Now Realtime events are shared across every server, so you can scale out safely.

The database could run out of connections

Before Under load, health checks and background jobs could exhaust the database's connection limit and take the app down.

Now Connection use is bounded and background work is capped so it can't starve the app.

Deploys cut off in-flight sends

Under the hood — built for real-world concurrency

12 GUARANTEES

The issues above were the visible symptoms. Underneath, the system is built to stay correct when thousands of things happen at the same instant — the class of bug that only appears under real load, with multiple servers and background workers all racing. Each of these is a guarantee the system now holds.

RACE

No double-send, even across servers

A recipient is claimed with one atomic, locked update before any message goes out — only the worker that wins the claim sends. Two overlapping jobs can't both deliver to the same person.

LOST UPDATE

The usage counter can't be corrupted

Every change is a single atomic database operation, never read-then-write — so two sends finishing at the same moment can't overwrite each other's count.

RACE

The plan limit can't be overshot

Reservations are serialized by a database row lock: twenty simultaneous sends at the cap resolve one at a time, and the ones over the line are cleanly rejected — not sent-then-regretted.

EXACTLY-ONCE

Each incoming webhook is handled once

A short-lived lease stops two workers processing the same event, and a re-delivered duplicate is recognized by its signature and skipped.

IDEMPOTENCY

Billing events can't double-apply

Every Stripe event ID is recorded before it's acted on, so a re-delivered "payment succeeded" is a no-op instead of a second charge or a second reset.

DISTRIBUTED

Rate limits hold across every server

WhatsApp's per-second cap is enforced by a shared counter in Redis, not per-server — and it reads its clock from Redis, so servers with skewed clocks still can't collectively over-send.

RECOVERY

Crashed mid-send work self-heals

If a worker dies holding a send, that recipient is automatically reclaimed after a timeout and retried — without re-sending anyone the batch already completed.

ATOMICITY

Money and delivery status commit together

A quota refund and the message's failure status are written in one transaction — a crash can never leave the counter refunded but the message still "sent," or vice-versa.

ISOLATION

Tenants can never see each other's data

Every query is automatically scoped to the caller's company at the database layer. There is no code path where one customer's contacts, messages, or tokens can surface for another.

CONSISTENCY

Message status only moves forward

Delivery updates can arrive out of order. A late "delivered" can never overwrite a "read," and a failed message can't be resurrected — the lifecycle is one-directional by design.

CONCURRENCY

No scheduled job runs twice at once

The campaign scheduler is guarded so that if one run overruns its minute, the next tick can't start a second copy alongside it and double-fire campaigns.

IDEMPOTENCY

Safe to retry, by design

Repeat an API send with the same key, or replay the same webhook, and the system returns the original result instead of doing the work twice — so automatic retries never cause duplicates.
