The Campaign Engine & How We Stay Off Meta's Ban Radar

How a campaign goes from Draft to delivered messages, the guard-rails that keep our WhatsApp numbers healthy, and how dozens of campaigns run side-by-side without tripping Meta's spam detection.

1 The Big Picture

A campaign is a scheduled, template-based blast to a deduplicated audience — sent in small paced batches by background jobs, never all at once.

Everything runs on Hangfire background jobs backed by Redis. The web request only creates the campaign; the actual sending is handed off to workers so we can pace, throttle, pause, and resume without holding an HTTP connection. Every read and write is tenant-isolated — because Hangfire has no HttpContext, jobs stamp CompanyId by hand and use IgnoreQueryFilters() deliberately.

Template-only

Every campaign must reference a Meta-Approved template. Unapproved → campaign fails fast at launch.

Batched, not bulk

Recipients are sent in chained batches of 50 (or 25 under stress), one batch enqueuing the next.

Rate-limited per number

A Redis token bucket caps sends per phone number — shared across all campaigns on that number.

Quality-aware

Meta's GREEN / YELLOW / RED quality rating directly modulates throughput, and can auto-pause.

2 The Send Lifecycle

Four jobs, each with one responsibility. A campaign flows through them like a pipeline.

A

CampaignSchedulerJob runs every minute

Cron.Minutely

Scans for Scheduled one-time campaigns whose time has arrived and enqueues a launch. Also acts as a watchdog: if a Running campaign still has queued recipients but no live Hangfire job, it re-enqueues a fresh batch (stall recovery).

B

CampaignLaunchJob once per campaign

enqueued by scheduler / immediate launch

Validates the template is Approved. Resolves the audience by taking the union of all contact lists + individually-added contacts and deduplicating. Bulk-inserts one CampaignRecipient row per unique contact in status Queued (idempotent on retry). Flips the campaign to Running and kicks off the first batch.

C

CampaignBatchSendJob the core sender · chains itself

AutomaticRetry(5), self-rescheduling

Pulls up to 50 queued recipients FIFO, runs every consent + rate-limit + quality gate, sends each through Meta's /messages endpoint, records the result, then enqueues the next batch until the audience is exhausted. This is where all the anti-ban logic lives (section 3).

D

CampaignPoisonHandlerJob on permanent failure

triggered after 5 exhausted retries

If a batch job dies for good, this marks the campaign Failed, flips all remaining queued recipients to Failed (CAMPAIGN_FAILED), and notifies the tenant. Nothing is left silently stuck.

Recipient status journey

Queued → Sent → Delivered → Read   (or  Failed / Skipped)

Delivery/read advancement comes from Meta status webhooks and is forward-only and idempotent — out-of-order or duplicate callbacks can never regress a status.

3 How We Minimize Getting Banned by Meta

Meta bans numbers that send too fast, message people who didn't opt in, or rack up blocks. We defend on all three fronts — automatically, inside the send loop.

3.1 — Rate limiting (the token bucket)

Before every single send, the job must acquire a permit from a Redis-backed token bucket keyed by phone number. It enforces two independent limits at once:

  • Per-second throttle — capacity 20, refills at 20/sec, so we never burst past Meta's per-second ceiling on a number.
  • 24-hour tier cap — a Redis set per calendar day counts unique recipients against the number's messaging tier (Tier250 / 1K / 10K / 100K / Unlimited). Counting is idempotent, so re-sends and retries never double-count.
// appsettings.json — the dials
"RateLimit": {
  "PerSecondCapacity": 20,      // burst ceiling per number
  "PerSecondRefill":   20,      // sustained permits/sec
  "FallbackRefill":    5,       // conservative, if Redis is down
  "CampaignWaitCapMs": 750      // max inline wait before reschedule
}
Never fail open. If Redis is unreachable, the limiter falls back to an in-process bucket using the conservative FallbackRefill = 5, so even degraded we stay comfortably under Meta's limits rather than flooding.

3.2 — How "20/sec" is actually paced

This is the part people assume wrong. We do not sleep a fixed gap after every message. The gap is emergent from the token bucket — it only appears when the bucket runs dry, and it's exactly the time needed to regenerate one token.

The bucket holds up to 20 tokens and refills continuously at 20/sec — i.e. one token every ~50ms. Each message costs one token. It starts full, so:

burst — bucket starts full (up to 20, zero gap) paced — one token every ~50ms
  • Phase 1 — the burst. The first ~20 messages fire essentially back-to-back, draining the full bucket. No gap between them.
  • Phase 2 — the steady gap. Once empty, the next send is denied and Redis returns a retryAfter ≈ 50ms (computed as (want − tokens) / refill). The job waits that exact amount inline, then retries — and by then a token has refilled. It settles into send → ~50ms → send → ~50ms… = 20/sec average.

The wait is precise, not a flat sleep: if the bucket had half a token, the wait is ~25ms, not 50. And waits are only taken inline while they're short — anything over CampaignWaitCapMs (750ms) parks the whole batch via reschedule instead of blocking a worker (see 3.3).

Why this can't be cheated by adding workers The bucket lives in Redis, keyed by phone number, and each check is one atomic Lua script. If four Hangfire workers send four batches on the same number at once, they all draw from the same 20 tokens. More workers or more campaigns never raise the rate — the number's combined output stays pinned at 20/sec.

3.3 — Pacing & jitter (don't look like a robot)

When a permit is denied, the job doesn't hammer. It saves progress and reschedules the whole batch:

  • Per-second throttle hit → wait 5–15 seconds with random jitter. The jitter matters: it stops several concurrent campaigns from waking in lockstep and spiking together.
  • Daily tier exhausted → sleep until just after the next UTC midnight, when the tier window resets.

Because recipients stay Queued, the rescheduled run resumes exactly where it stopped — no double-sends.

3.4 — Quality-rating gates (listen to Meta's signal)

A health-check job refreshes each number's QualityRating. The batch sender reacts to it before sending:

GREEN Full speed

Normal batch size of 50, full rate.

YELLOW Back off

Batch size halved to 25 — we voluntarily reduce pressure to let quality recover.

RED Stop

Campaign is auto-paused and the tenant is notified. We refuse to keep sending on a damaged number.

3.5 — Consent & reachability gates (only message people who agreed — and who exist)

For every recipient, three checks run before a permit is even requested:

  • No opt-in (HasOptedIn == false) → Skipped · NO_CONSENT
  • Opted out (IsOptedOut == true) → Skipped · OPT_OUT
  • Not a WhatsApp user (IsWhatsAppValid == false) → Skipped · NOT_ON_WHATSAPP

Messaging non-consenting users is the fastest route to blocks and bans — so we never do it, even if they're on the list. The third gate is about reachability: once Meta has told us a number isn't on WhatsApp (see 3.8), we skip it for free on every future send instead of burning a send — or a precious daily-tier slot — on a dead number.

3.6 — Reading Meta's error codes & reacting

When Meta returns a policy error, we don't blindly retry — we interpret it and contain the blast radius:

Campaign-level errors pause just the offending campaign; account-level errors deactivate the whole number connection so nothing else keeps pushing into a restriction.

3.7 — When Meta says "slow down" (130429)

130429 (throughput rate limit) and 131056 (per-recipient pair limit) are transient — Meta is asking us to ease off, not flagging a violation. The message was not sent, so treating these as permanent failures would silently drop deliverable messages. We handle them exactly like our own internal throttle:

  • The recipient stays Queued — nothing is marked failed.
  • Progress is persisted and the whole batch is rescheduled with a 5–15s jittered back-off.
  • When it wakes, it resumes from the exact same recipient — duplicate-safe, nothing lost.
In practice this should rarely fire. Our token bucket already paces sends below Meta's throughput ceiling, so we usually never see 130429. The handler is a safety net for the edge cases — a number shared with another integration, a freshly throttled new number, or a Redis hiccup that desyncs the limiter. Either way, the response is back-off-and-retry, never lose the message.

3.8 — Learning who isn't on WhatsApp (131026)

A common question: can't we check whether a number is on WhatsApp before we send? On Meta's Cloud API the answer is no — there is no pre-send registration lookup. (The old On-Premises API had a /contacts endpoint; Meta removed it and never ported it, specifically to stop number-harvesting.) So the only signal we ever get is post-send: error code 131026 — "message undeliverable / recipient is not a WhatsApp user."

Rather than waste that signal, we learn from it once and never repeat the mistake:

  • When a send response or a delivery-status webhook returns 131026, we stamp the contact IsWhatsAppValid = false (with a WhatsAppInvalidAt timestamp).
  • From then on, the reachability gate in 3.5 skips that contact with NOT_ON_WHATSAPP — costing zero sends and, crucially, zero daily-tier slots.
  • The stamp is idempotent: duplicate or out-of-order webhooks only set it once, and it's written by mutating the tracked entity (the webhook batch's single SaveChanges commits it — no mid-handler save).
Post-send, not pre-send — but only once per number The very first message to a non-WhatsApp number will always fail; there's no way around that on the Cloud API. But every campaign after that skips the number automatically. Over time the audience self-cleans, and real deliverable contacts stop sharing their daily-tier budget with dead numbers.
Existing contacts default to reachable. The IsWhatsAppValid column ships with a default of true — we never assume a number is dead until Meta tells us so. The flag only ever flips on a real 131026.

4 Precautions — The Full Checklist

Beyond rate limiting, these are the defensive choices baked into the system.

✅ Approved templates only

Launch fails fast if the template isn't Meta-approved — no unapproved content ever leaves.

✅ Audience dedup

Union of lists + individuals is deduplicated so no contact is messaged twice in one campaign.

✅ Idempotency keys

Recipients carry idempotency keys; retries and webhook replays never cause a re-send or status regression.

✅ Quota pre-checks

A subscription gate verifies plan quota before launch; a daily job warns 72h/48h/24h/6h before a big send would exceed quota.

✅ Quality health checks

A scheduled job refreshes quality rating + tier every ~15 min so gates act on fresh data.

✅ Pause / resume / cancel

Mid-loop pause checks mean a human can stop a campaign instantly without corrupting state.

✅ Graceful degradation

Redis outage → conservative local limiter. The system slows down, it never floods.

✅ Tenant isolation

Every job manually scopes to CompanyId — one tenant's campaign can never touch another's data or number.

5 How Multiple Campaigns Run Together

Many campaigns can be live at once. The key insight: the rate limit belongs to the phone number, not the campaign.

If three campaigns all send through the same WhatsApp number, they don't each get their own quota — they share one token bucket and one daily tier counter for that number. That's exactly what Meta cares about: total volume per number, regardless of how many campaigns produced it.

Why this is safe by design Because the lock key is the phone number, the combined output of every campaign on a number is automatically capped at Meta's limit. You physically cannot misconfigure two campaigns into doubling the send rate.

The concurrency model

  • Per-number rate limiter — all campaigns on a number queue through the same bucket; the 24h tier set is shared, so a contact reached by campaign A isn't re-counted by campaign B that day.
  • Independent batch chains — each campaign chains its own batches (A's batch 1 → A's batch 2), so campaigns interleave rather than block one another.
  • No campaign-level locking — they don't serialize; the Hangfire worker pool (max(4, cores×2) workers) runs many batches concurrently, and the rate limiter is the single point that keeps the shared number within bounds.
  • Jitter prevents thundering herd — the 5–15s randomized reschedule stops concurrent campaigns from all retrying on the same tick.
ScenarioBehaviour
3 campaigns, same numberShare one bucket + one daily tier. Total rate stays ≤ Meta's cap.
Campaigns on different numbersIndependent buckets — run fully in parallel at full speed each.
One campaign hits YELLOWOnly that number's campaigns slow down; others unaffected.
One campaign hits a policy errorThat campaign pauses; siblings on the same number keep going (unless it's an account-level restriction).

Let's trace one campaign to a 2,000-contact list on a number with the default Tier1K tier and a healthy GREEN rating. The interesting part: 2,000 is bigger than the 1,000/day tier cap, so the engine spreads it across two days automatically.

Step 0 — Launch (audience is frozen)

CampaignLaunchJob validates the template, then takes the list and deduplicates it. Say 40 were duplicates already reached by another list and 60 never opted in — those get filtered/skipped. The job bulk-inserts ~1,900 CampaignRecipient rows in Queued (we'll round to 2,000 for the walkthrough). Campaign flips to Running and the first batch is enqueued.

The timeline

DAY 1 · 00:00

Batches 1 → 20 fire (recipients 1–1,000)

Each batch grabs 50 queued recipients FIFO. Before every send the job acquires a token-bucket permit. At 20 permits/sec, 50 messages clear in ~2.5s, so 1,000 messages take roughly 50 seconds of actual send time (plus tiny jitter pauses whenever the per-second bucket momentarily empties). Each success writes a Message row, flips the recipient to Sent, and bumps SentCount.

DAY 1 · ~00:01

Batch 21 hits the daily tier cap

The 1,001st permit request comes back DailyTierExceeded — the number has used its full Tier1K allowance for the UTC day. The job does not fail: it persists progress and reschedules the whole batch for just after the next UTC midnight. The remaining ~1,000 recipients stay Queued exactly where they are.

DAY 1 · rest of day

Campaign sits idle, 1,000 / 2,000 sent

Nothing is stuck or lost. The watchdog scheduler sees a Running campaign that's intentionally parked and leaves it. Delivery/read webhooks for the first 1,000 keep arriving and advance those recipients to Delivered / Read.

DAY 2 · 00:05

Batches 21 → 40 fire (recipients 1,001–2,000)

The daily tier set resets at UTC midnight. The rescheduled batch wakes, permits flow again, and the final ~1,000 messages send in another ~50 seconds.

DAY 2 · ~00:06

Campaign → Completed

No recipients remain Queued, so the batch job stops chaining and marks the campaign Completed. Final tallies: Sent / Skipped (no-consent & opt-out) / Failed are all visible on the campaign stats.

DAY 1 — 1,000 sent DAY 2 — 1,000 sent
The takeaway You never have to think about any of this. You point the campaign at 2,000 contacts and press go — the engine paces it to ~20/sec, respects the 1,000/day tier by splitting across two days, and resumes precisely where it paused. No flooding, no double-sends, no manual babysitting.

7 Watching a Campaign Live

While a campaign is sending, you don't have to guess how far along it is — the stats refresh on their own and a progress bar fills in real time.

Every recipient's status lives in the database, so a campaign's progress is just a live rollup of those rows. The API exposes it at GET /campaigns/{id}/stats (CampaignService.GetStatsAsync), which counts recipients by status straight from CampaignRecipient — no extra bookkeeping that could drift out of sync with reality.

What the rollup returns

FieldMeaning
totalRecipientsAudience size frozen at launch
queuedNot yet processed — the work remaining
sent / delivered / readForward-only delivery progress (advanced by webhooks)
failed / skippedTerminal outcomes (errors, no-consent, opt-out, not-on-WhatsApp)
deliveryRate / readRateDerived percentages for at-a-glance health

The progress bar

"Progress" is simply how much of the audience has left the queue:

processed = total − queued
percent   = round(processed / total × 100)

The campaign-stats dialog leads with a bar showing processed of total (percent%) — e.g. "730 of 1,000 (73%)" — above the per-status count grid. While recipients remain queued it shows a "Sending…" spinner; once the queue drains it flips to "Completed."

Status-aware polling

The frontend hook (useCampaignStats) doesn't poll blindly. It refetches the rollup every ~4 seconds while queued > 0 — so the numbers and the bar climb on their own with no manual refresh — and then stops automatically the moment the queue hits zero (every recipient has reached a terminal status). A finished campaign isn't polled forever.

Why queued === 0 is the right stop signal. A recipient only leaves Queued when it reaches a terminal-for-sending state (Sent/Delivered/Read/Failed/Skipped). So an empty queue means there's nothing left for the engine to do on this campaign — exactly when live polling should wind down. (Delivery/read webhooks may still trickle in afterwards; reopening the dialog picks them up.)

8 Failure Handling & Recovery

Resilience is layered so nothing gets stuck, lost, or double-sent.

  • Rate-limit backoff isn't a failure — progress is persisted and the batch reschedules; the job never throws on a throttle.
  • Per-recipient failures are isolated — one bad recipient is marked Failed with its error code; the batch keeps going.
  • Job-level retries — AutomaticRetry(5) on the batch job for transient infra hiccups.
  • Poison handler — after retries are exhausted, the campaign and its remaining recipients are cleanly marked Failed and the tenant is notified.
  • Stall watchdog — the per-minute scheduler re-enqueues any Running campaign that has queued recipients but lost its live job.
  • Forward-only status webhooks — Sent → Delivered → Read advance idempotently; duplicates and out-of-order callbacks are safe.
