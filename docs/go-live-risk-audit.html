WhatsApp CRM — Go-Live Risk Audit

A concurrency-, correctness- and operations-focused review of the wa_api (.NET 8) backend and wa_web (Next.js) frontend, done to answer one question: what breaks when we start sending for real customers at volume? Duplicate sends were the seed example — this is the full picture around it.

Bottom line. The foundations are genuinely strong — tenant isolation, the transactional webhook inbox, atomic quota increments, distributed rate limiting and JWT hardening are all well-built (see What's already solid). The go-live risk is concentrated in concurrency the current design doesn't actually prevent (duplicate sends, quota over-spend), a one-line JSON bug that silently disables all campaign anti-ban handling, secrets stored in plaintext, and a handful of single-instance-only assumptions that break the moment you add a second container. Two findings from the automated pass were false positives and were removed after reading the code — documented at the end for transparency.
Remediation update — 2026-07-05. Findings are tagged inline below with a ✓ Fixed / ◐ Partial badge and a resolution note; untagged items remain open.

Fixed: C2, C3 · H1, H2, H4, H7, H8, H9, H10, H11, H12 · M1–M14, M16, M18, M20, M21 · L1, L9. Partial: C1 (no hard meter ceiling), H3 (encryption code-complete; needs ops to provision a prod key + rotate tokens), H5 (idempotency done; ordering guard + Fail/dead-letter open), H6 (exact-sub done; legacy fallback kept), M19 (JWT shortened; CSP/hub-token open). Still open: M11 (CI-gated migrations — process), M15/M17 (fold into C1 / replica-count decision). Lows L1–L5 & L9 fixed; L6/L7/L8/L10 left as documented dispositions (defensive-test / safe-direction / ops / product-decision).

Billing model confirmed: no auto-renew — a subscription runs to its period end, then the tenant must subscribe again (accumulate-until-expiry). This resolved M21 (no dunning applies) and L1 (delete the reset job). Most fixes remain uncommitted; 6 migrations must be applied to prod before deploy.

Critical — fix before go-live

Each of these causes real, customer-visible or money-losing harm under ordinary production conditions (retries, concurrency, restarts). Not theoretical.

Critical◐ Partial C1. Quota is never enforced atomically, and campaigns aren't gated at send time → paid quota is a soft suggestion Billing / Quota
Evidence
Common/Subscriptions/SubscriptionGate.cs:39 Common/Subscriptions/SubscriptionMeter.cs:48–54 Features/Campaigns/Jobs/CampaignBatchSendJob.cs:41–471 CampaignService.cs:181 (Recurring skips the check)
What's wrong
The gate does a read-only used >= quota check, the message sends, then the meter does an unconditional SET used = used + n. The meter never checks the ceiling. Worse, the campaign batch loop never calls the gate at all — quota is checked once at launch, and Recurring campaigns skip even that. When no active sub exists, the meter silently no-ops, so post-cancellation campaign sends go out free and uncounted.
Failure scenario
A tenant on a 1,000-message plan fires 20 concurrent sends near the cap — all read used = 999, all pass, all send, all increment → real spend past the paid quota. Launch two campaigns at once and both clear the same launch check. A campaign running for hours keeps sending after the subscription expires or a Stripe payment-failed webhook marks it inactive mid-run.
Fix
Make the meter the enforcement point: UPDATE ... SET used = used + n WHERE id=@id AND used + n <= quota + credits RETURNING id; treat 0 rows as QUOTA_EXCEEDED. Invert order to reserve-then-send (refund on send failure — the refund plumbing already exists). Re-check active + not-expired + remaining quota at the top of every campaign batch, including Recurring.
◐ Partially fixed — 2026-07-05
The meter is now a race-free atomic increment, and the campaign batch enforces quota at send time — it pauses the campaign and notifies when usage reaches quota+credits, Recurring included. Still open: the meter has no hard ceiling (it increments unconditionally), so concurrent HTTP sends right at the cap can still marginally overshoot — true reserve-then-send at the meter is not yet implemented. 2e80888
Critical✓ Fixed C2. Campaign duplicate sends under concurrency — the dedup guard is advisory only Send pipeline
Evidence
CampaignBatchSendJob.cs:126–167, 285–326 AppDbContext.cs:244, 247 (Message: non-unique) BaseEntity.cs (no RowVersion) IDistributedLockService — never acquired in the send path
What's wrong
Duplicate protection is a non-atomic read-check (alreadyMessaged HashSet) followed by send-then-flip. Verified against the schema: the sent Messages table has no unique index on (CampaignId, ContactId) — only the CampaignRecipient table does (line 562), and the batch only updates those rows so it never trips. There's no concurrency token, and the fully-built IDistributedLockService is registered in DI but never used anywhere in the send path (dead code).
Failure scenario
Hangfire is at-least-once. A worker heartbeat loss / long GC pause / container restart mid-batch makes the in-flight job visible again; a second worker picks up the same batch, both load the same 50 Queued recipients, both compute empty alreadyMessaged, both call Meta, both insert a Message (nothing stops it). Every recipient delivered twice and metered twice. The recent "record batch job id on launch" fix closed the scheduler-vs-launch path, not this re-dispatch path. A crash between the Meta 200 and the DB commit (line 326) resends on retry even single-worker.
Fix
Defense in depth: (1) add a partial-unique index Messages(CampaignId, ContactId) WHERE CampaignId IS NOT NULL so a resend fails at INSERT and reconciles; (2) claim-then-send — UPDATE CampaignRecipients SET Status='Sending' WHERE Id=@id AND Status='Queued', send only if 1 row affected; (3) wrap the batch in the existing AcquireAsync($"campaign-send:{id}") lock. WhatsApp Cloud API has no server-side idempotency key, so a local uniqueness guard is the only real defense.
✓ Fixed — 2026-07-05
Claim-then-send implemented: an atomic UPDATE CampaignRecipients SET Status='Sending' WHERE Id=@id AND Status='Queued' gates every Meta call, so only the batch that wins the claim sends; a stale Sending claim self-heals after 5 min. Backed by a partial-unique index on Messages(ExternalMessageId) as an INSERT-level backstop and run-scoped dedup. 2e80888
Critical✓ Fixed C3. Meta error codes parsed as strings but returned as numbers → every campaign anti-ban handler is silently dead Rate-limiting / Meta API
Evidence
CampaignBatchSendJob.cs:736 — .GetProperty("code").GetString() contrast WabaHealthCheckJob.cs:116 uses .GetInt32() swallowing catch at CampaignBatchSendJob.cs:738
What's wrong
Meta returns error.code as a JSON number. Calling GetString() on a Number element throws, the throw is swallowed, and errorCode falls back to "HTTP_400". So every classifier that keys on the numeric code returns false: account-restriction (368/131031), spam/ecosystem pause (131048/131049), transient throttle (130429/131056), undeliverable (131026).
Failure scenario
Meta flags the number for spam (131048) — the single most important anti-ban signal — and the campaign keeps blasting because the pause never fires → number gets quality-downgraded, rate-limited, or blocked by Meta. A "slow down" throttle is treated as a permanent per-recipient failure, so deliverable messages are silently dropped. A restricted WABA keeps sending the whole audience.
Fix
One-line class of fix: read the code as a number when ValueKind == Number and normalize to string, mirroring the health-check job. Add a unit test feeding a real body ("code":131048) that asserts the campaign pauses. This single bug defeats the entire policy layer the rest of the code carefully builds.
✓ Fixed — 2026-07-05
Extracted ParseMetaErrorCode that reads error.code whether Meta sends it as a JSON number or string, restoring every policy classifier (spam-pause 131048, restriction, throttle, undeliverable). Regression-tested in MetaErrorCodeParseTests.cs. ed0eeec

High✓ Fixed H2. A poison batch re-enqueues every minute forever — no terminal failure state Send pipeline
Evidence

High◐ Partial H3. Meta access tokens & App Secrets stored in plaintext; the "encryption" key is 32 zero-bytes and never used Security
Evidence
WabaConnection.cs:47–51, 74–78WabaConnectionService.cs:90–91, 135–139appsettings.Development.json:24–26 (Key = base64 of all-zero)no AesGcm/Decrypt/Encryption:Key reader anywhere in source
Detail
The column is only named EncryptedAccessToken — values are stored as-is. Every tenant's long-lived Meta token (full send capability, real billing) and per-app HMAC secret (used to verify inbound webhooks) sit in cleartext in Supabase and in every pg_dump backup. Any DB/backup leak = full takeover of every tenant's WhatsApp sending and the ability to forge inbound webhooks. The provisioned Encryption:Key is a public all-zero placeholder — "fixing" the code with it would be worthless.
Fix
Encrypt both columns at rest (AES-256-GCM via ITokenProtector, or ASP.NET Data Protection / pgcrypto / KMS). Generate a real key (openssl rand -base64 32), keep it only in the server .env/secret store, migrate existing rows, and rotate every token & secret since they've lived in plaintext.
◐ Code complete — 2026-07-05
Added ITokenProtector (AES-256-GCM, enc:v1:-prefixed) applied as an EF value converter on WabaConnection.EncryptedAccessToken + AppSecret, so all ~10 call sites keep using plaintext and every new write is encrypted at rest. Transparent + non-breaking: legacy plaintext still decrypts, empty stays empty, and a startup WabaSecretEncryptionBackfill encrypts existing rows. Falls back to a passthrough protector (with a loud warning) when no key is set, so nothing breaks pre-provisioning. Round-trip tested (TokenProtectorTests.cs). Ops to finish (data stays plaintext until then): provision a real base64 32-byte Encryption:Key in the prod .env, deploy (backfill runs), then rotate every Meta token & app secret since they lived in cleartext. uncommitted

High◐ Partial H5. Stripe: no event-id idempotency and no ordering guard → cancelled subscriptions resurrected, billing events silently dropped Billing / Stripe

Verification & corrected false positives

Two findings from the automated pass were checked against the actual code and removed. Flagging them so nobody "fixes" a non-bug.

Corrected“Quota refund isn't in a transaction → double-refund on retry”
Why it's not a bug
WebhookProcessingJob.cs:65–70 does open BeginTransactionAsync around dispatch + MarkProcessedAsync + commit; the refund's raw SQL enlists in that ambient transaction, so refund and Failed-status commit atomically. Retries are idempotent (a retry sees the message already Failed). Also OnAttemptsExceeded = Fail here (not Delete). The refund logic is sound — only its null-metered fallback (H6) is a real issue.
Corrected“Dev secrets file isn't covered by .gitignore → risk of accidental commit”
Why it's not a bug
.gitignore lines 35 & 38 explicitly ignore appsettings.Development.json and contabo.md; git check-ignore confirms both are ignored and neither is tracked. Repo-leak vector is closed. The remaining real risk is the values themselves being plaintext at rest — covered by H3.

What's already solid (don't over-warn)

Verified strong
  • Tenant isolation: every tenant entity carries a CompanyId global query filter; all 60+ IgnoreQueryFilters() sites were individually verified to re-scope by a trusted CompanyId — no cross-tenant leak or IDOR found. Tenant identity comes only from JWT claims, never client input.
  • Transactional webhook inbox: raw-body HMAC with fixed-time compare + fail-closed on missing secret, unique EventSignature partial index for replay dedup, atomic claim/lease so two workers can't process one row, forward-only status model, dead-lettering with a durable Dead state, fast-ACK 200 with async processing.
  • Quota increment itself is race-free (single atomic SET x = x + n); the refund is atomic GREATEST(0, x-n), forward-only, and pins the exact metered subscription. (The gap is the missing ceiling and campaign gating, not the increment.)
  • Distributed rate limiting: Redis Lua token bucket keyed per phone-number, reads time from Redis to avoid clock skew, never fails open (bounded in-process fallback), idempotent daily-cap counting.
  • Auth hardening: full JWT validation (issuer/audience/lifetime/key) with fail-fast on a short key, bcrypt, no user-enumeration, refresh-token rotation with revoke-before-reissue, CSPRNG tokens, WABA tokens never serialized to clients. CORS is an explicit allowlist with no wildcard.
  • Send-window / RED-rating pauses, per-batch idempotency reads, and reschedule-on-throttle are duplicate-safe by design (recipients stay Queued, resume-from-where-stopped).
  • Ops-aware infra: Npgsql pool intentionally capped under the Supabase 15-client limit (with documented rationale), split liveness/readiness health endpoints, Redis AbortOnConnectFail=false so a startup blip doesn't crash the app.
