WhatsApp CRM — Go-Live Risk Audit

A concurrency-, correctness- and operations-focused review of the wa_api (.NET 8) backend and wa_web (Next.js) frontend, done to answer one question: what breaks when we start sending for real customers at volume? Duplicate sends were the seed example — this is the full picture around it.

Bottom line. The foundations are genuinely strong — tenant isolation, the transactional webhook inbox, atomic quota increments, distributed rate limiting and JWT hardening are all well-built (see What's already solid). The go-live risk is concentrated in concurrency the current design doesn't actually prevent (duplicate sends, quota over-spend), a one-line JSON bug that silently disables all campaign anti-ban handling, secrets stored in plaintext, and a handful of single-instance-only assumptions that break the moment you add a second container. Two findings from the automated pass were false positives and were removed after reading the code — documented at the end for transparency.

Critical — fix before go-live

Each of these causes real, customer-visible or money-losing harm under ordinary production conditions (retries, concurrency, restarts). Not theoretical.

Critical C1. Quota is never enforced atomically, and campaigns aren't gated at send time → paid quota is a soft suggestion Billing / Quota
Evidence
Common/Subscriptions/SubscriptionGate.cs:39 Common/Subscriptions/SubscriptionMeter.cs:48–54 Features/Campaigns/Jobs/CampaignBatchSendJob.cs:41–471 CampaignService.cs:181 (Recurring skips the check)
What's wrong
The gate does a read-only used >= quota check, the message sends, then the meter does an unconditional SET used = used + n. The meter never checks the ceiling. Worse, the campaign batch loop never calls the gate at all — quota is checked once at launch, and Recurring campaigns skip even that. When no active sub exists, the meter silently no-ops, so post-cancellation campaign sends go out free and uncounted.
Failure scenario
A tenant on a 1,000-message plan fires 20 concurrent sends near the cap — all read used = 999, all pass, all send, all increment → real spend past the paid quota. Launch two campaigns at once and both clear the same launch check. A campaign running for hours keeps sending after the subscription expires or a Stripe payment-failed webhook marks it inactive mid-run.
Fix
Make the meter the enforcement point: UPDATE ... SET used = used + n WHERE id=@id AND used + n <= quota + credits RETURNING id; treat 0 rows as QUOTA_EXCEEDED. Invert order to reserve-then-send (refund on send failure — the refund plumbing already exists). Re-check active + not-expired + remaining quota at the top of every campaign batch, including Recurring.
Critical C2. Campaign duplicate sends under concurrency — the dedup guard is advisory only Send pipeline
Evidence
CampaignBatchSendJob.cs:126–167, 285–326 AppDbContext.cs:244, 247 (Message: non-unique) BaseEntity.cs (no RowVersion) IDistributedLockService — never acquired in the send path
What's wrong
Duplicate protection is a non-atomic read-check (alreadyMessaged HashSet) followed by send-then-flip. Verified against the schema: the sent Messages table has no unique index on (CampaignId, ContactId) — only the CampaignRecipient table does (line 562), and the batch only updates those rows so it never trips. There's no concurrency token, and the fully-built IDistributedLockService is registered in DI but never used anywhere in the send path (dead code).
Failure scenario
Hangfire is at-least-once. A worker heartbeat loss / long GC pause / container restart mid-batch makes the in-flight job visible again; a second worker picks up the same batch, both load the same 50 Queued recipients, both compute empty alreadyMessaged, both call Meta, both insert a Message (nothing stops it). Every recipient delivered twice and metered twice. The recent "record batch job id on launch" fix closed the scheduler-vs-launch path, not this re-dispatch path. A crash between the Meta 200 and the DB commit (line 326) resends on retry even single-worker.
Fix
Defense in depth: (1) add a partial-unique index Messages(CampaignId, ContactId) WHERE CampaignId IS NOT NULL so a resend fails at INSERT and reconciles; (2) claim-then-send — UPDATE CampaignRecipients SET Status='Sending' WHERE Id=@id AND Status='Queued', send only if 1 row affected; (3) wrap the batch in the existing AcquireAsync($"campaign-send:{id}") lock. WhatsApp Cloud API has no server-side idempotency key, so a local uniqueness guard is the only real defense.
Critical C3. Meta error codes parsed as strings but returned as numbers → every campaign anti-ban handler is silently dead Rate-limiting / Meta API
Evidence
CampaignBatchSendJob.cs:736 — .GetProperty("code").GetString() contrast WabaHealthCheckJob.cs:116 uses .GetInt32() swallowing catch at CampaignBatchSendJob.cs:738
What's wrong
Meta returns error.code as a JSON number. Calling GetString() on a Number element throws, the throw is swallowed, and errorCode falls back to "HTTP_400". So every classifier that keys on the numeric code returns false: account-restriction (368/131031), spam/ecosystem pause (131048/131049), transient throttle (130429/131056), undeliverable (131026).
Failure scenario
Meta flags the number for spam (131048) — the single most important anti-ban signal — and the campaign keeps blasting because the pause never fires → number gets quality-downgraded, rate-limited, or blocked by Meta. A "slow down" throttle is treated as a permanent per-recipient failure, so deliverable messages are silently dropped. A restricted WABA keeps sending the whole audience.
Fix
One-line class of fix: read the code as a number when ValueKind == Number and normalize to string, mirroring the health-check job. Add a unit test feeding a real body ("code":131048) that asserts the campaign pauses. This single bug defeats the entire policy layer the rest of the code carefully builds.

High — fix before or immediately after launch

Serious correctness, money, security or availability issues that will surface within the first days of real traffic.

High H1. Recurring campaigns send exactly once, then silently deliver nothing forever Send pipeline
Evidence
CampaignLaunchJob.cs:104–125CampaignBatchSendJob.cs:138–143, 451–460
Detail
newRecipients = target contacts minus everyone who already has a CampaignRecipient row regardless of status. On completion a Recurring campaign resets to Scheduled but recipient rows are never cleared. Next firing → newRecipients is empty → a batch enqueues, finds zero Queued rows, "completes." Core feature is broken and fails silently.
Fix
Introduce a CampaignRunId and dedup within a run (preferred, keeps history), or re-queue existing recipients (Status→Queued, clear MessageId/ErrorCode) at each firing.
High H2. A poison batch re-enqueues every minute forever — no terminal failure state Send pipeline
Evidence
CampaignBatchSendJob.cs:29 (OnAttemptsExceeded=Delete)CampaignPoisonHandlerJob.cs — never enqueued (dead code)CampaignSchedulerJob.cs:63–88 (stall sweeper)
Detail
A deterministic fault (bad template payload, NRE) throws every attempt. After 5 the job is deleted; the campaign stays Running with Queued rows; the sweeper re-enqueues a minute later; repeat forever. The campaign is never marked Failed, the tenant is never notified, and each cycle re-sends pre-fault recipients (compounds C2).
Fix
Wire an IElectStateFilter/continuation to invoke the already-written CampaignPoisonHandlerJob on attempts-exceeded, or add a recovery counter so the sweeper gives up and marks the campaign Failed + notifies.
High H3. Meta access tokens & App Secrets stored in plaintext; the "encryption" key is 32 zero-bytes and never used Security
Evidence
WabaConnection.cs:47–51, 74–78WabaConnectionService.cs:90–91, 135–139appsettings.Development.json:24–26 (Key = base64 of all-zero)no AesGcm/Decrypt/Encryption:Key reader anywhere in source
Detail
The column is only named EncryptedAccessToken — values are stored as-is. Every tenant's long-lived Meta token (full send capability, real billing) and per-app HMAC secret (used to verify inbound webhooks) sit in cleartext in Supabase and in every pg_dump backup. Any DB/backup leak = full takeover of every tenant's WhatsApp sending and the ability to forge inbound webhooks. The provisioned Encryption:Key is a public all-zero placeholder — "fixing" the code with it would be worthless.
Fix
Encrypt both columns at rest (AES-256-GCM via ITokenProtector, or ASP.NET Data Protection / pgcrypto / KMS). Generate a real key (openssl rand -base64 32), keep it only in the server .env/secret store, migrate existing rows, and rotate every token & secret since they've lived in plaintext.
High H4. invoice.paid resets quota to 0 on every delivery → repeated free quota refills Billing / Stripe
Evidence
StripeWebhookProcessingJob.cs:200–205 (reset outside the insert/update branch)second reset path at :104–110
Detail
The MessagesUsedThisPeriod = 0 reset runs on every delivery of invoice.paid — including Stripe's routine redeliveries/retries of the same invoice. Each redelivery zeroes usage mid-period → the tenant gets a fresh full quota repeatedly, for free. A late invoice.paid for an old invoice wipes the current period.
Fix
Reset only when the event genuinely opens a new period (guard on invoice period-start vs CurrentPeriodStart), dedupe by Stripe event id (H5), and consolidate to a single reset path.
High H5. Stripe: no event-id idempotency and no ordering guard → cancelled subscriptions resurrected, billing events silently dropped Billing / Stripe
Evidence
StripeWebhookController.cs:45–46 (enqueue by type+json, no event-id dedup)StripeWebhookProcessingJob.cs:96–133, 141–156:18 — OnAttemptsExceeded = Delete
Detail
No processed-events table. Stripe delivers at-least-once and out-of-order: a stale subscription.updated (active) arriving after subscription.deleted re-activates a cancelled sub. Separately, if a subscription.created/invoice.paid fails 5× (e.g. missing StripePriceId mapping) the job is deleted with no dead-letter and no alert — a paying customer ends up with no synced subscription, discovered only by complaint.
Fix
Persist processed Stripe event ids in a unique-indexed table (mirror the Meta inbox). Ignore events older than stored state; never move a locally-cancelled sub back to Active from a stale update. Change OnAttemptsExceeded to Fail and add dead-letter alerting.
High H6. Refund fallback credits the current active subscription for messages that were never metered Billing / Webhooks
Evidence
MessageStatusWebhookHandler.cs:99–108
Detail
When MeteredSubscriptionId is null (the pre-2026-07-03 campaign/FB sends that were never metered — see project memory) a failed-unbilled message falls back to decrementing today's active subscription. A historical, never-counted message that later gets a failed webhook gifts the tenant a free send. Given the known historical under-count, this fallback actively worsens accounting.
Fix
Only refund when MeteredSubscriptionId is non-null; drop the "current active" fallback — a message that never incremented a counter must not decrement one.
High H7. Unknown/deactivated phone_number_id returns 401 → Meta can disable the shared webhook for all tenants Webhooks
Evidence
WhatsAppWebhookController.cs:64–69 (returns Unauthorized)WabaConnectionService.cs:62–68 (filters IsActive → deactivated = null)
Detail
One shared webhook URL serves the whole platform. Meta treats any non-2xx as a delivery failure and, on sustained failures, disables the webhook subscription — degrading ingestion for every company. Triggers: a number onboarded on Meta's side but not yet in our DB, or an admin temporarily deactivating a connection (every correctly-signed inbound for that number now 401s and is lost).
Fix
For a validly-signed but unroutable payload return 200 and drop/park it; reserve non-2xx strictly for signature failures and genuine persistence errors. Consider not filtering IsActive in the webhook lookup, or persist-before-route so a re-activation can replay.
High H8. No brute-force protection on auth; long-lived 8-hour JWTs; verify prod isn't still on the dev signing secret Security
Evidence
AuthController.cs:19–34 (login/refresh, no throttle)no AddRateLimiter/UseRateLimiter in Program.csAccessTokenExpiryMinutes: 480contabo.md:198,439 (JWT secret rotation TODO still open)
Detail
/auth/login accepts unlimited guesses per IP/account — combined with a known seed admin email this enables password spraying with no lockout. Access tokens are stateless for 8h, so deactivations/role changes don't take effect until expiry. If prod still uses the committed dev HS256 secret, anyone with it can forge SuperAdmin tokens.
Fix
Add ASP.NET rate limiting (sliding window keyed by IP+email) on login/refresh + per-account lockout. Shorten access-token lifetime to 15–60 min and lean on refresh rotation. Confirm the prod .env JWT secret is a strong random value; rotate if not.
High H9. SignalR has no Redis backplane → realtime chat breaks silently the moment you run >1 instance Infra / Realtime
Evidence
Program.cs:138–139 (AddSignalR, no AddStackExchangeRedis)ChatNotifier.cs:15–17 (in-process group push)
Detail
Redis is already wired for cache/Hangfire/locks/rate-limit, but not for SignalR. The instant a second replica exists (or a blue/green overlap during deploy), a webhook processed on instance B pushes only to B's clients; tenants on instance A get nothing until manual refresh. Fails with no error.
Fix
Add .AddStackExchangeRedis(redisConnection) to the SignalR builder. One line — and it's the thing standing between you and safe horizontal scaling.
High H10. DB connection exhaustion: a second unbounded pool from health checks, plus Hangfire/web contention under the Supabase 15-client cap Infra / DB
Evidence
Program.cs:44–50 (app pool capped at 10)HealthCheckExtensions.cs:14–16 (raw string, default pool max 100)HangfireExtensions.cs:31–35 (WorkerCount = cores×2)
Detail
The health check uses a different connection string with no pool params → a second Npgsql pool (default max 100). Concurrent readiness probes can push total PG clients past Supavisor's 15 → sorry, too many clients. Separately, Hangfire workers (8 on a 4-vCPU box) draw from the same 10-slot EF pool as HTTP requests; a campaign burst can starve the API.
Fix
Point the health check at the pooled string (or a tiny Max Pool Size=2). Cap WorkerCount (e.g. 4) or move prod to Supavisor transaction mode (port 6543) before raising the pool. Load-test a campaign concurrent with dashboard traffic.
High H11. Transient network / 5xx errors permanently fail campaign recipients — no retry policy Rate-limiting / Meta API
Evidence
CampaignBatchSendJob.cs:743–746 (NETWORK_ERROR → matches no classifier → Failed at :415)Program.cs:101–105 (MetaGraph client: 15s timeout, no Polly)
Detail
A 2-second DNS hiccup or a 503 from Meta during a 10K-recipient campaign permanently marks every recipient hit during the blip as Failed — deliverable customers never get the message, with no automatic re-attempt.
Fix
Classify NETWORK_ERROR / HTTP 5xx / 408 / 429 as transient — leave the recipient Queued and take the reschedule-with-backoff path. Do not add blind Polly retries to the non-idempotent send POST until C2's uniqueness guard is in place (it would amplify duplicates).
High H12. Access-token expiry (190) mid-campaign burns the whole remaining batch one failure at a time Rate-limiting / Meta API
Evidence
MetaPolicyErrorCodes.cs (no 190 classifier)WabaHealthCheckJob.cs:87–90 (handles 190, but only every 15 min)
Detail
Even after C3 is fixed, a 190 (expired/invalid token) during a send falls through to per-recipient Failed, failing the entire remaining audience individually instead of halting once. Pairs with H3 (token management).
Fix
Add 190 (and account-restriction codes) to a fatal branch that pauses the campaign, marks the connection Invalid, and halts immediately.

Verification & corrected false positives

Two findings from the automated pass were checked against the actual code and removed. Flagging them so nobody "fixes" a non-bug.

Corrected“Quota refund isn't in a transaction → double-refund on retry”
Why it's not a bug
WebhookProcessingJob.cs:65–70 does open BeginTransactionAsync around dispatch + MarkProcessedAsync + commit; the refund's raw SQL enlists in that ambient transaction, so refund and Failed-status commit atomically. Retries are idempotent (a retry sees the message already Failed). Also OnAttemptsExceeded = Fail here (not Delete). The refund logic is sound — only its null-metered fallback (H6) is a real issue.
Corrected“Dev secrets file isn't covered by .gitignore → risk of accidental commit”
Why it's not a bug
.gitignore lines 35 & 38 explicitly ignore appsettings.Development.json and contabo.md; git check-ignore confirms both are ignored and neither is tracked. Repo-leak vector is closed. The remaining real risk is the values themselves being plaintext at rest — covered by H3.

What's already solid (don't over-warn)

Verified strong
  • Tenant isolation: every tenant entity carries a CompanyId global query filter; all 60+ IgnoreQueryFilters() sites were individually verified to re-scope by a trusted CompanyId — no cross-tenant leak or IDOR found. Tenant identity comes only from JWT claims, never client input.
  • Transactional webhook inbox: raw-body HMAC with fixed-time compare + fail-closed on missing secret, unique EventSignature partial index for replay dedup, atomic claim/lease so two workers can't process one row, forward-only status model, dead-lettering with a durable Dead state, fast-ACK 200 with async processing.
  • Quota increment itself is race-free (single atomic SET x = x + n); the refund is atomic GREATEST(0, x-n), forward-only, and pins the exact metered subscription. (The gap is the missing ceiling and campaign gating, not the increment.)
  • Distributed rate limiting: Redis Lua token bucket keyed per phone-number, reads time from Redis to avoid clock skew, never fails open (bounded in-process fallback), idempotent daily-cap counting.
  • Auth hardening: full JWT validation (issuer/audience/lifetime/key) with fail-fast on a short key, bcrypt, no user-enumeration, refresh-token rotation with revoke-before-reissue, CSPRNG tokens, WABA tokens never serialized to clients. CORS is an explicit allowlist with no wildcard.
  • Send-window / RED-rating pauses, per-batch idempotency reads, and reschedule-on-throttle are duplicate-safe by design (recipients stay Queued, resume-from-where-stopped).
  • Ops-aware infra: Npgsql pool intentionally capped under the Supabase 15-client limit (with documented rationale), split liveness/readiness health endpoints, Redis AbortOnConnectFail=false so a startup blip doesn't crash the app.
